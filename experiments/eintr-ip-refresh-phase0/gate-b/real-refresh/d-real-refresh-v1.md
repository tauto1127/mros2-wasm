**Incomplete / do not treat as GateB proof.** No production files were edited. The focused scratch runs measured important continuation behavior for a real UDP socket through `socket → checkpoint → connect → getsockname → close`, and one run also completed a later actual refresh. But I did **not** measure a contender attempting the coordinator after restore: in the successful run the fixture's contender attempted before the checkpoint and exited. A viable common try-claim therefore needs a narrow exported core-try operation (or other code in that translation unit); calling the blocking `LOCK_TCPIP_CORE()` is not a nonwaiting coordinator. Do not take this ordinary core mutex and then invoke a blocking local-IP getter that takes it again.

This establishes target pthread mutex trylock continuation behavior for the fixture, not the integration details or startup safety of a production accessor.

## Cleanup/error-path reasoning and boundaries

Source reasoning maps the owner cleanup obligations: failure of `socket()` returns with no fd; invalid destination, failed `connect()`, or failed/invalid `getsockname()` each closes its opened fd before returning failure; success closes after copying the IP. The outer proposed owner must unlock exactly once regardless of probe result, e.g. a single cleanup/return path after `probe_local_ip()`. The scratch successful replay exercises unlock after success, not the error cleanup branches. The C/R did not deliberately cause connect or getsockname to fail; it cannot claim measured replay-error cleanup.

The fixture's checkpoint hook is scratch-only, and no temporary hook was placed in production. The test did not measure real refresh contention with ordinary core-lock owners, integration lock ordering, `netif_default` startup-before-core-init behavior, IP/mask reader data races, RTPS propagation/endpoint-reader synchronization, or changed-IP applied-state semantics. It also does not establish arbitrary host/network or multi-NIC behavior. No RTPS sockets were recreated.
