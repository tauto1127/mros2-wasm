# 計画：mROS 2 Wasm復元後のトピック通信を再確認する

状態：計画のみ。未実施。

## 目的と位置づけ

Wasm上のmROS 2アプリをチェックポイントから同じIPで復元した後、二つのトピックを使うアプリ通信が続くかを、両側の受信処理に残る同じメッセージIDで判定する。

2026-09-24の[探索的試験](../../../2026-09-24/runs/exploratory-cr-01/report.md)で確認できたのは、復元後のUDP受信口の再作成と`recvfrom()`の成功までだった。保存前からアプリ通信が成立していた証拠がなく、通信復旧の判定には使えない。後日の[run-04](../../../2026-09-27/runs/run-04/report.md)と[run-07](../../../2026-09-27/runs/run-07/report.md)は、それぞれ1回の同一IPでのアプリ往復に成功している。この計画は、同じ条件での追加の独立試行である。9/17の実行ファイルは正確に特定できていないため、9/17の完全再現や、その失敗原因の特定とは扱わない。

## トピック通信の合格条件

| トピック | 送信 | 成功を示す受信記録 |
|---|---|---|
| `/to_linux` | Wasmが連番IDを含む`std_msgs/msg/String`を送る | native mROS 2アプリのsubscriber callbackに同じIDと本文が現れる |
| `/to_stm` | nativeアプリが受け取った本文をそのまま返信する | Wasmアプリのsubscriber callbackに同じIDと本文が現れる |

一つの完全往復は、同じIDと本文について、次の順序を両側のアプリログで確認できたものとする。

`Wasm APP publish_begin → native peer_receive → native peer_echo_publish_return → Wasm APP callback`

run-04の既存判定スクリプトは主にIDの集合を照合する。今回の合格候補10件では、ログ上の本文一致とイベントの順序も追加で確かめ、ID集合の一致だけで合格にしない。

`peer`は既存ログのイベント名にだけ残す。この文書では通信相手のnative mROS 2アプリを指す。`publish_begin`や返信の関数が戻った記録だけでは、相手の受信成功と判定しない。`recvfrom()`成功、トピック一覧、ネットワーク上のパケットも補助証拠であり、合格判定は両側のsubscriber callbackで行う。

保存前は60秒以内に異なるIDで10件以上の完全往復を確認する。続く30秒間、チェックポイントを行わずに新しいIDで10件以上の完全往復を確認する。この二つを通過した場合だけチェックポイントへ進む。

復元後は、復元プロセスを確認してから90秒以内に、異なる新しいIDで10件以上の完全往復を確認する。チェックポイントを送る直前までのWasmの最大送信IDを`N`とし、復元後の判定には`N`より大きく、復元後のWasmログに`APP publish_begin`があるIDだけを使う。復元直後に残っていた古い受信や、90秒を過ぎた観測は合格件数に含めない。

## 固定する条件

| 項目 | 条件 |
|---|---|
| 実行場所 | この物理ホスト上のDockerのみ |
| ネットワーク | 既存の`mros2-cr-net`、`172.18.0.0/16`。ネットワーク自体は変更しない |
| IP | Wasm側`172.18.0.3`、通信相手`172.18.0.5`。Wasmは同じコンテナ・同じIPで復元する |
| 通信相手 | native POSIX版mROS 2。ROS 2の`rclpy`アプリには置き換えない。チェックポイント中も動かし続ける |
| アプリ | Wasmが`/to_linux`へ約1秒ごとに連番付き本文を送信し、通信相手が同じ本文を`/to_stm`へ返信する |
| メッセージ・設定 | `std_msgs/msg/String`、Domain 0、[run-04 metadata](../../../2026-09-27/runs/run-04/metadata.md)に記録された実行条件 |
| 実行ファイル | run-04と同じ`iwasm`、Wasmアプリ、nativeアプリ。実行前に3件のSHA-256をrun-04 metadataと照合する |

run-04で使った照合値は、`iwasm`が`96c9f1ae89a29e8b2ab87eccdb54df4f7e6203be6945413cc19052df09f3920a`、Wasmアプリが`0a725f9a303650a64358964a6f6ef0cd84d5cc82734fcbeb87ec8f7dd1d8df76`、nativeアプリが`8f41fa890a8da84c9000772bba2fb8287553bea1311ccf7fd4d5d0daed7b27b1`である。現在のソースツリーのcommitだけを実行ファイルの証明に使わない。必要なファイルがない、照合値が違う、IPやコンテナ名が使用中の場合は開始前に停止して報告する。

## 実行順序と中止条件

1. 新しい実験IDと、`2026-09-28/runs/`以下の未使用ディレクトリを決める。既存の`run-04`、`run-06`、`run-07`やステージ済みのファイルを変更しない。Dockerネットワーク、IPの使用状況、イメージID、実行ファイルの照合値、run-04記録に基づく各ソースの版とビルド時の未コミット変更、利用する起動コマンドを記録する。
2. 実験用のnative通信相手、受動的なパケット観測プロセス、Wasmを起動する。すべての実行コマンド、コンテナ名、プロセスID、開始時刻を記録する。アプリログはWasm側とnative側を独立に保存する。
3. 保存前の60秒ゲートと30秒の無チェックポイント区間を判定する。どちらかが未達ならチェックポイントを行わず、最後に確認できた通信段階を報告して終了する。通信相手のトピック情報も採取するが、それ単独では合否を決めない。
4. 対象のWAMRプロセスを確認し、`N`と時刻を記録してチェックポイントを実行する。終了状態とSocket Journalの記録を保存する。通信相手は起動したままにする。
5. 同じWAMR実行ファイルとWasmアプリを同じIPで復元する。Socket Journal再生、UDP受信口の状態、通信相手の受信・返信、Wasmの受信を個別に記録し、90秒の合格条件を判定する。未達なら、その1回の結果として保存する。設定を変えた再試行はこの実験に混ぜない。
6. 新しく作ったコンテナと観測プロセスだけを停止・削除し、共有ネットワークの状態を確認する。チェックポイント本体は実験固有の`/tmp`領域に残し、そのファイル一覧とSHA-256をGit管理下に記録する。

[run-04の手順と判定スクリプト](../../../2026-09-27/runs/run-04/README.md)を参照してよい。ただし、スクリプトに固定された`run-04`のコンテナ名や保存先は確認し、今回の新しい実験IDを使う。実行ファイルを変更・再ビルドして条件を合わせ直すことはしない。

## 残す証拠と報告形式

新しい実験ディレクトリには、`plan.md`、実際の手順、`metadata.md`、`report.md`、生ログを保存する。生ログには保存前と復元後のWasmログ、native受信・返信ログ、ゲートの開始時刻・終了時刻・判定・一致したIDと本文、保存・復元の状態、トピック情報、受動的なUDP観測、Dockerの前後状態、実行ファイルの照合値を含める。大きなチェックポイント本体はGitに含めない。

`report.md`の冒頭には、対象の試行が合格したか、保存前・復元後それぞれで両トピックの受信処理に同じIDが何件出たかを記す。少なくとも1件は、Wasm送信・native受信・native返信・Wasm受信の生ログへの参照を並べる。不合格なら、IDごとに最後に確認できた段階を示す。90秒の判定後の観測は分けて記載する。

この計画の実行には、別の物理マシン、ホストの経路・ファイアウォール変更、既存Dockerネットワークの再設定、Heptabaseへの書き込み、Gitのcommit・pushを含めない。既存のステージ済み変更には触れない。
